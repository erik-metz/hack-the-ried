# Heltec GPS end-device bring-up, 2026-11-08

Board: Heltec V4.3, USB hardware MAC `F8:5B:1B:A1:75:D8`, ESP32-S3, 16 MB
flash and 2 MB QSPI PSRAM, as reported by esptool. User confirmed local profile
`heltec-v-001.h`; original TTN DevEUI `70B3D57ED0079D8B`, private companion
`025D152A493EFC0D`. Keys were never printed or compiled into the image.

## Recovery and exact firmware

The original gateway source `hardware/dev-gateway/v1` was left unchanged. Its
complete 16777216-byte flash was saved privately in the ignored local
`hardware/sensor-node/heltec-v4/build/recovery/gateway-original.bin`, SHA256
`5cd26a5f41664f1a7a247658fb2086a8890f400edd1112d140bf9e31545e5205`.
The backup includes sensitive original configuration and is mode600 in a
mode700 recovery directory. It is not a distributable firmware artifact.

The new firmware A uses 442528 bytes, SHA256
`b35f0eed7251bdb095f8928b42c776660d05e6060a42cf5dfe03f8e382671493`.
It compiled with ESP32 Arduino 3.3.11 / RadioLib 7.7.1, was scanned for all
original/private/group key byte and ASCII sequences (none present), and was
flashed and verified by esptool on the identified board. USB provisioning
acknowledged `PROFILE stored; restarting`. NVS was not erased.

## Device checks

Serial confirmed OLED initialization (`DISPLAY ready=1`), successful new TTN
activation (`TTN JOIN ... joined=1`), and checksum-valid NMEA on **RX39/TX38,
9600 baud**. The initial no-fix status progressed to a fresh real fix with four
satellites, then five. This corrects the previous gateway sketch's opposite
UART defaults, without editing that older source.

The user independently confirmed the visible `Heltec GPS v1` display, TTN/GPS
status lines and working GPS. Exact real coordinates are deliberately omitted
from this committed report. GPS coordinates remain visible on the device and
are sent to the user's explicitly selected TTN application.

## TTN reception

Device: `heltec-v4-001`, application: `my-gps-tracker-2026`. Original DevEUI
remains on TTN, DevAddr `260B9539`, FPort44, SF7BW125.

- **10:04:15.325979744 UTC / 11:04:15 local:** initial no-fix packet was
  successfully processed and forwarded, RSSI -79 dBm / SNR 7.75 dB.
- **10:06:09.487206308 UTC / 11:06:09 local:** first-fix packet was successfully
  processed and forwarded, RSSI -79 dBm / SNR 11.75 dB, application counter1.
  Local decoding of these actual received bytes with the committed formatter
  returned no errors, `gps_fix=true`, valid latitude and longitude fields,
  four satellites, firmware1, and approximately 4.235 V battery.

Those first packets preceded installation of the device-level GPS formatter
and therefore show the old production decoder's FPort-10 error in their event
history. The new device-level formatter was then tested in TTN with a 24-byte
no-fix fixture on port44 and saved; TTN confirmed `Payload formatter updated`.
The next real uplink at **10:11:16.242313859 UTC / 11:11:16 local** was
successfully decoded and forwarded directly by TTN: `gps_fix=true`, latitude
and longitude present, altitude47 m, satellites5, HDOP2.3, fix age0 s,
approximately 4.306 V battery, firmware1, application counter2. RSSI was -86 dBm
and SNR 2.25 dB. TTN subsequently emitted `Forward location solved message`
with GPS as its source at 10:11:16.262151330 UTC. This independently confirms
actual GPS position reception and automatic TTN location extraction, beyond
local serial or simulated decoder checks. Exact position bytes/coordinates
are not included in this public report.

The application-wide formatter and backend were left unchanged. The existing
webhook is disabled according to the later TTN event; this test ends at TTN.

## Private update setup

A distinct random Heltec multicast group was created on the Pi, retaining all
RAK memberships, keys and counters:

- Name `kamue-ttn-update-v3-heltec`.
- ID `fcbed4d6-002b-47b9-b922-4c795973625e`.
- Private companion `025D152A493EFC0D`, explicit gateway `98FE54FFFE63713B`.
- Independent state `/state/v3-heltec-group-id.json`, ClassC, 869.525 MHz, DR5.

Registration was sealed locally to the Pi's X25519 transfer key and decrypted
only on the Pi. The router private allowlist retained all four RAK companions
and added this Heltec companion. Its original TTN identity was not redirected.
After the gateway restart, serial confirmed private activation (`UPDATE JOIN
... joined=1; TTN remains active`) and port42 boot feedback.

An actual Heltec firmware transfer was **not** performed in this bring-up.
Do not interpret private activation as proof of OTA application. Future tests
must use a Heltec-specific A/B bundle and `send.py --heltec`; RAK images and
multicast groups are not interchangeable with this board.

## Validation and remaining scope

The real C++ GPS encoder was compiled and tested against its JavaScript decoder,
including signed coordinates/altitude, full uint32 counters, no-fix omission,
stale age and malformed fields. The new hardware CI runs those checks. Existing
private multicast tests, including mixed-group/state rejection, passed.
Local firmware compile, actual upload, USB identity storage, GPS and OLED bring-up,
TTN raw application reception and private activation all succeeded.

Battery runtime, sleep behavior, RF power-meter calibration and a moving range
test remain unverified. The current prototype leaves OLED/GPS/ClassC active.
