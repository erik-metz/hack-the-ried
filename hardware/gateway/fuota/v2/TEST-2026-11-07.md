# Private on-air delta updates and RAK3112 bench provisioning

Verified on 2026-11-07 with the USB-powered RAK3112-003 and the RAK2287 in
`kamue-lora-pi`. This is the project's experimental FPort-43 protocol, not a
TS004/TS005 interoperability or multicast test.

## Result

The device initially ran firmware 1/value 111 from `ota_0`. ChirpStack sent a
delta manifest and four changed blocks (indices 1, 342, 344, 3005). The receiver
reported all 3006 image blocks present, verified the complete target SHA-256,
selected `ota_1` and rebooted. Serial output then reported firmware 2/value 222,
`OTA running=ota_1`, a restored LoRaWAN session, and a value-222 uplink. Independently,
the Pi sender observed that actual uplink via ChirpStack MQTT and reported:

```text
Status {"state": 3, "session": 1307009673, "received": 3006, "total": 3006, "missing": []}
VERIFIED: firmware 2, value 222 received from 70B3D57ED0079D88
```

Both images are 384768 bytes. The exact common binaries are kept locally under
the ignored `hardware/sensor-node/rak3112/fuota/build/rak3112-003/chirpstack/`:

| Image | SHA-256 |
| --- | --- |
| `1/dummy.ino.bin` | `5fd7d37c6f78a83c340d6413f75483748c2ebf8fa1ab0325dea718e2b958c305` |
| `2/dummy.ino.bin` | `9c54aeba58ff0f46d39f241528a7870b0a2176383d8049fd2cb6dc615731efd6` |

Firmware source: `aec18305c89ff2fbc2a7c0da07f61f1bd617dfb9`. Build configuration:
ESP32 core 3.3.11, RadioLib 7.7.1, ESP32-S3 hardware CDC, 16 MiB flash,
OPI PSRAM, private network 2. Device identity and RadioLib security counters
remained in NVS across the firmware replacement. Use this exact A binary for
the next board; rebuilding A can change its base hash.

## Gateway and recovery

The gateway base image was pinned to
`ghcr.io/erik-metz/hack-the-ried-gateway:sha-d5008847a085a3f2f83958072abc16bc23052f9d`,
with the v2 router bind-mounted from source `5e500b4`.
After completion, Docker health was `healthy`; `radio_ready`, `station_connected`,
`lns_connected`, and a fresh `private_lns_connected` were all true. This proves
concurrent LNS connections; it does not establish a new production TTN uplink
after switching this test device to the private network.

Watchtower is stopped for the experiment. The host guardian remains running
and accepted the new healthy image. The verified original TTN image is also
retained as `kamue-gateway:fuota-verified-ttn-baseline`. The original deployment
manifest, credentials and state remain under `/home/alpha/hack-the-ried/gateway`.
Use the README rollback procedure to return to the original single-LNS setup.

The first attempt exposed two real integration issues: Gateway Bridge omits
zero-valued radio fields and represents unused DRs differently from TTS; and
patching a cloned NOR-flash sector requires erase/read-modify-write. Tests now
cover both. Before the successful retry, the guardian automatically restored
the old TTN deployment after repeated candidate restarts. It was rearmed with
the known-good image retained. The first complete transfer failed its target
hash and correctly retained firmware 1; no invalid image was selected.

Private registrations were transported as authenticated ciphertext to a key
generated on the Pi. Device credentials were not logged or committed. The
common A/B binaries were scanned for the selected raw and derived device keys.

## Two-device follow-up

RAK3112-004 was identified separately by its ESP32-S3 USB MAC ending `26:AC`
(RAK3112-003 ends `26:F0`). It was flashed with the exact common A image above
and provisioned over USB with its own `rak3112-004` private identity. Serial
confirmed a new OTAA session and firmware 1/value 111. The board was then moved
to a USB power adapter; RAK3112-003 was reconnected to the PC and reset to that
same A image. Its NVS identity and security counters were retained.

Both devices were active in ChirpStack before the update. The same verified
A-to-B delta was used with a fresh transfer session `3089432311`. A single
bounded shell job invoked the unicast sender for 003, then for 004, stopping
on any failure. Each device reported state 2 with all 3006 blocks present,
then state 3 after target hash validation and boot selection. ChirpStack MQTT
independently confirmed each post-reboot firmware/value uplink:

```text
VERIFIED: firmware 2, value 222 received from 70B3D57ED0079D88
VERIFIED: firmware 2, value 222 received from 70B3D57ED0079D89
```

RAK3112-003 serial also confirmed the switch from `ota_0` to `ota_1`, restored
session and value-222 uplink. RAK3112-004 was powered without a PC during its
entire radio update, so its result is established by the authenticated network
status and independent uplink, rather than a connected serial monitor.

The job completed successfully. Its operational artifacts remain private on
the Pi: `/home/alpha/.local/share/kamue-fuota-v2/delta-two-device.json` and
`/tmp/kamue-fuota-two-device.log` (the latter is temporary). No credentials are
included in this report. No firmware source changed for this follow-up.

Afterward, the gateway was healthy, its guardian active, the TTN LNS connected
and the private LNS connected. The two health records were respectively 4.3
and 1.5 seconds old. This confirms updates to two independently provisioned
clients while both were powered. Delivery was sequential unicast (four radio
data blocks per device), **not multicast**; standard TS004/TS005 FUOTA remains
outside this verified prototype.

Final bench state: RAK3112-003 on PC USB, RAK3112-004 on the USB power adapter,
both running firmware 2/value 222. Neither needs to be unplugged for continued
uplink observation.

## RAK3112-005 provisioning

The third board was separately identified by USB MAC `3C:DC:75:6F:25:9C` and
provisioned from the local, ignored `rak3112-005.h` profile. Its DevEUI
`70B3D57ED0079D8A` was checked for uniqueness against 003 and 004. The exact
verified A image above was flashed; the common image contains no device keys.
The private identity was then written through USB into NVS.

On the Pi, independently derived private keys were provisioned into the same
lab tenant/application using the sealed file transport. Existing 003/004 keys
and sessions were retained. The gateway's test whitelist now includes all
three DevEUIs, using the same pinned base image and v2 overlay.

Serial verification on 005 showed:

```text
FUOTA-LAB firmware=1 value=111 protocol=lab1
DevEUI=70b3d57ed0079d8a
OTA running=ota_0 target=ota_1 size=6291456
JOIN state=-1118 joined=1
UPLINK value=111 counter=0 state=2 downlink=0
```

This verifies its private OTAA join and initial uplink from the device side.
No radio firmware update was attempted on 005 during this provisioning step;
its current baseline remains firmware 1/value 111. Unlike the two-device update
above, no independent MQTT firmware/value observation was collected for 005.

Current bench state: 003 and 004 powered by USB adapters on firmware 2/value 222;
005 on PC USB on firmware 1/value 111, ready for a subsequent update test.
The serial monitor has been closed so the USB port is available. No firmware
source or Heltec gateway code was changed for this step.
