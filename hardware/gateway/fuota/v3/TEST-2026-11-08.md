# RAK4 migrated to TTN telemetry and separate update identity

On 2026-11-08 the attached USB board was identified as RAK3112-004 by hardware
MAC `3C:DC:75:6F:26:AC`. The saved common firmware A from the RAK5 test was
flashed and verified by esptool without erasing NVS:

- Firmware 1 / test value 111, image size 386816 bytes.
- SHA256 `b521db0244735323aa180e84b10995fca850982dab73a790b85c27a614ec60f4`.
- TTN DevEUI `70B3D57ED0079D89`.
- Independent private control DevEUI `02629E770438454A`.

`dual_provision.py rak3112-004 --port ...` acknowledged `PROFILE stored;
restarting`. The USB command stored the new dual identity in NVS, preserving
LoRaWAN security state. It reused the existing local multicast group keys.
The common image contains no device profile. Future uploads that preserve NVS
can reuse that stored identity; a new board or migration from the previous
profile format needs explicit initial provisioning.

The encrypted companion registration was transferred to the Pi and decrypted
only there. Provisioning exposed a duplicate gateway-membership insertion:
this ChirpStack server reports it as INTERNAL. Commit `f3f562e` instead queries
existing device and gateway memberships, checks result bounds, and inserts only
missing members. Its regression test verifies that repeat provisioning retains
the existing group counter and does not attempt duplicate membership inserts.
Actual repeat provisioning then completed successfully on the Pi.

The gateway private allowlist became
`70B3D57ED0079D88,02629E770438454A,021F6846A820B440`:
RAK3's previous private identity remains routed to ChirpStack, while RAK4 and
RAK5's original identities route to TTN. Their separate companions route to
ChirpStack. RAK4 joined existing multicast group
`e2e1945e-29e4-4f49-b578-280338ca727f` without resetting its frame counter.
The existing pinned gateway image and guardian were retained.

## RAK1 migration, with stable-state recovery

RAK3112-001 was identified by USB MAC `3C:DC:75:6F:25:C0` and flashed with the
same saved common A image. Its original TTN DevEUI is `70B3D57ED007984B` and its
private companion is `02837438D5995DF7`. USB provisioning acknowledged the new
identity. Encrypted registration, private group membership and gateway restart
all completed on the Pi. Its private allowlist now contains four companions:
`02837438D5995DF7,0237C5608461F069,02629E770438454A,021F6846A820B440`.

Unlike the previous lab boards, RAK1 had been running the stable sensor sketch,
which persists RadioLib state under `rak3112lw`. Initial TTN joins were rejected
with `DevNonce is too small` (07:49:00 and 07:50:07 UTC), because the dual sketch
had not imported this existing state. No server nonce check was reset and NVS
was not erased.

The new `migrate_stable_state` USB maintenance sketch validated the saved stable
nonce and session buffers against the provisioned identity, copied the newer
nonce state and associated session to the identity-bound destination, and
verified both by reading them back. Serial reported `MIGRATION verified`. The
source was retained. Its compiled partition table was compared byte-for-byte
with the saved common A table and matched. The exact common A firmware was then
restored and verified by esptool; the maintenance program is no longer running.

Afterward USB serial independently confirmed:

- Firmware 1 / value 111, original TTN identity and separate private companion.
- `TTN JOIN state=-1117 joined=1` (session restored).
- `TTN UPLINK firmware=1 value=111 counter=0 state=0`.
- `UPDATE JOIN state=-1118 joined=1; TTN remains active`.
- `UPDATE feedback port=42 state=1`.

The final independent TTN application-reception check remains **unverified** in
this record: browser control started returning `cgWindowNotFound` after the
security-state migration, including after reconnecting the control runtime.
Successful serial transmission/session activation alone is not counted as
proof of TTN application reception. The RAK1 TTN Live data verification tab
could not be closed for the same reason. No FUOTA transfer was initiated.

Validation: maintenance sketch compiled for ESP32-S3; source-state validation,
copy and readback ran successfully on the actual board; 44 stable protocol
checks, four FUOTA decoder/receiver checks, and seven Python profile tests passed.
Current installed states: RAK1 A/111, RAK3 A/111, RAK4 A/111, RAK5 B/222.
