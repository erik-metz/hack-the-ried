## Observed radio transfer

The initial sender stopped before transmitting: ChirpStack rejected a device
list query without its application ID. Commit `34885f6` includes that ID and a
regression assertion. The corrected sender completed successfully.

Private multicast group: `e2e1945e-29e4-4f49-b578-280338ca727f`, Class C,
869.525 MHz, DR5. Transfer session: `126934155`.

- Frame 1 started the delta, reporting 3018 of 3022 image blocks already present.
- Frames 2–5 delivered changed blocks 1, 343, 345, 3021.
- Frame 6 requested status; RAK5 reported state 2, 3022/3022, no missing blocks.
- Frame 7 applied the image. USB serial observed result 3 and software reboot.
- The sender subsequently printed `VERIFIED update companion
  021F6846A820B440: firmware 2, value 222` and the shell reported the process done.

forwarding through `hack-the-ried-kamue`, DevAddr `260BB36B`, FPort 42:

The post-update uplink had RSSI -71 dBm and SNR 11.75 dB. This is evidence of
TTN application reception after a real private multicast firmware replacement.
The existing production decoder still rejects lab FPort 42 and the webhook
fails for this dummy payload. Both were deliberately left unchanged: this test
ends at TTN reception, as requested. It does not verify backend ingestion,
standard LoRa Alliance FUOTA interoperability, or production update security.
